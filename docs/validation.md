## Amplitude and Mixpanel identity: e-mail user id and anonymous-device merge — 2026-10-29T23:30Z

- Same treatment as PostHog, on request. User id = verified e-mail (setting `identity`: `email` default, `person_id`). The SDK captures, with analytics consent only, the Amplitude device id (`AMP_<prefix>` cookie: `btoa(encodeURIComponent(JSON))`, `deviceId`; verified in `amplitude/Amplitude-TypeScript` `analytics-core/src/storage/cookie.ts` and `cookie-name.ts` on 2026-10-29) and the Mixpanel device id (`mp_<token>_mixpanel`: `encodeURIComponent(JSON)` with `$device_id`/`distinct_id`; verified in `mixpanel/mixpanel-js` `src/utils.js` and `src/mixpanel-core.js`). Amplitude: `device_id` on the event (Amplitude docs: an event with both ids applies the user's Amplitude ID to the device's anonymous events). - Tests: `tests/test_analytics_identity.py` (12), SDK 63 pass (both cookie formats, consent gating, rejects), two contract tests updated (the e-mail now appears only as the user id). Full suite **2,452 passed**; `ruff` clean.

## PostHog identity: e-mail distinct_id and anonymous-visitor merge — 2026-10-29T22:10Z

- Reported from the live preview: `distinct_id` was the platform's person UUID, which would create a second PostHog person next to the one the website already tracks. Now `distinct_id` is the registrant's verified e-mail (per-integration setting `identity`: `email` default, `person_id` on request), and the SDK captures the visitor's PostHog `distinct_id` from the `ph_<token>_posthog` cookie with analytics consent (`attribution.IDENTIFIER_PURPOSE`), stored like the GA client id; the adapter sends it as `$anon_distinct_id` on `$identify` (also when the profile group is off), which is PostHog's documented merge path. Malformed ids are ignored, an id equal to the distinct_id is not sent, nothing is ever invented.
- Tests: `tests/test_posthog_identity.py` (13), SDK `sdk/test` 63 pass (cookie parsing, consent gating, rejects), existing PostHog contract test updated. Full suite **2,438 passed**; `ruff` clean.
