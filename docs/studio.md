# Studio (marketer UI)

`/studio/` replaces Django admin for day-to-day work (admin stays for maintenance). Django templates + vanilla JS/CSS (`webinars/templates/studio/`, `webinars/static/studio/`), no build step.

- **Access**: session login at `/studio/login/`. Every view uses `webinars/studio/access.py`: read permission per page, write permission for POST, CSRF on every POST. Analysts are read-only; PII is masked unless `webinars.view_person`. Integrations, deliveries and API keys need Administrator permissions. Team management (invites, roles, member emails, deactivation) is **superuser-only**, matching `roles.py` (role groups never get auth write permissions); nobody edits their own role.
- **Content**: events from realistic starters (feature release, workshop, interview; `webinars/samples.py`) with AIDA fields, sessions, publish/unpublish with readiness checks, preview, form builder (add/remove/reorder fields, labels, help, required, options; versions in use are saved as new versions), hosts/topics (Administrators can delete a host that is on no published event; draft events lose the host), registrations, reports.
- **Sessions**: schedule/reschedule, join destination (never shown to attendees), waiting room toggle + lead time, live controls Automatic / Hold / Open now / End, room URL to share. Each session in the event editor's Sessions list links to **Waiting room & admission** (`/studio/sessions/<id>/#room-title`) with its on/off/needs-join-URL state, and to **Embed on your site**. The session page shows a readiness note (off / needs join URL / ready). The provider join URL stays visible only to roles with `change_occurrence`; the `/w/<code>/` room link is the attendee-facing link.
- **Registration button** (event editor): `register_label` (submit text, blank = “Register”) and `confirm_label` (shown when a recognised visitor has nothing left to fill in, blank = “Confirm my RSVP”). These are event fields, so they are revisioned and form versions stay immutable. Up to 60 characters of one-line plain text, with no `<`, `>` or `` ` `` and no control characters (`validation.validate_cta_label`). They appear in the public event API as `cta.register`/`cta.confirm`, in the management API/MCP as `registerLabel`/`confirmLabel`, in revision snapshots and in webhook `event.cta`, in the preview, and in the embed snippet (button text plus `data-confirm-label`).
- **Cover image** (event editor, Basics): upload a PNG/JPEG/WebP **or** paste an https URL, never both (both at once → 400; a URL is rejected while an upload is attached until “Remove the uploaded image” is ticked). Limits: 2 MB upload, 4096 px per side, 12 megapixels, 3 MB after re-encoding (`webinars/covers.py`). Files are checked by magic bytes and fully decoded with Pillow, then re-encoded from pixels, which strips EXIF/XMP/ICC metadata. SVG, GIF, animated and polyglot files are rejected. Uploads are held in memory only (`FILE_UPLOAD_HANDLERS`, one file per request) and stored in PostgreSQL (`CoverImage`), so there are no media volumes or writable paths in the read-only container, and backups include covers. The cover row is created in the same transaction as the event revision, so a failed save leaves no orphan. Served publicly at `/media/covers/<uuid>.<ext>`, looked up by random UUID only (no file paths), with `nosniff`, `CSP: default-src 'none'; sandbox`, `Cache-Control: public, max-age=31536000, immutable` and an ETag. Covers are immutable and kept after replacement, so old revisions and webhook payloads keep resolving. Draft covers are reachable only by their unguessable URL. `heroImageUrl` (public API, revisions, webhooks) is the absolute `PUBLIC_BASE_URL` cover URL when an upload exists. Upload is studio-only; the management API exposes read-only `coverImageId`. Admins can delete stale cover rows only once no event references them (`PROTECT`).
- **Embed on your site** (session page → `/studio/sessions/<id>/embed/`, any role with `view_occurrence`): a copyable `webinar-form.js` snippet generated from the event's form version (occurrence ID, form version, every field, SMS consent with disclosure version, register/confirm CTA labels; all text HTML-escaped) plus the script tag for `/static/webinar-sdk/webinar-form.js`. It contains no API keys or join/waiting-room links. Nothing is deployed automatically: the marketer's server must serve `/webinar-api/*` same-origin via the proxy (`sdk/proxy/server.js`), with a `proxy`-scoped key from Studio › API keys in `PROXY_API_KEY` and exact `PROXY_ALLOWED_ORIGINS`. See docs/browser-integration.md.
- **Tracking & GTM** (Connect › `/studio/tracking/`, Administrators and superusers: same `view_apikey` permission as the proxy key it depends on; Editors and Analysts get 403 and no nav entry): a copyable **site-wide** GTM Custom HTML tag, distinct from the per-session form embed. It inlines the public `webinar-sdk/gtm-loader.js` helper plus a server-built JSON config and, on every fire, loads `webinar-form.js` once (retrying after a failed load), reads consent from the newest plain `window.dataLayer` message that owns the configured key (default `webinarConsent`; exact `granted`/`true` only, malformed newest message denies, no `{{variable}}` references, no eval, no prototype lookups, or always denied) and binds embedded forms rendered since the last fire. The page shows a separate copyable example of the message the CMP must push (literal values; not an automatic CMP integration). Settings are native GET inputs (script URL, proxy path, consent source, dataLayer consent key) validated server-side (same-origin path or https URL only, no credentials/query/fragment/`..`/`//`/backslashes; identifier-only key with reserved names refused); nothing is persisted and invalid values fall back to defaults with an error summary. A non-platform script host is called out visibly above the tag. The page explains prerequisites (same-origin proxy, `proxy`-scoped key kept server-side), what is functional (recognition call) versus consent-gated (attribution, including the referrer), GTM triggers (DOM Ready + the consent custom event, Unlimited firing, after-render event for SPAs), the per-session script conflict, Preview/CSP checks, and states that Studio cannot verify the tag is live. The tag contains no keys, links or personal data; the embed page cross-links to it. See docs/browser-integration.md §6.
- **Progressive disclosure**: rarely-needed settings sit behind `details.disclosure` blocks (opened server-side when a value or error is present) and `data-reveals` controls; the `hidden` attribute always wins over display classes.
- **Connect**: integrations (choosing a native provider on the create page reloads it with that provider's settings and credential boxes and hides the webhook-only fields; webhook destinations, event types, payload groups, consent requirements, field mapping rows, encrypted signing secret generate-once/paste, encrypted credentials by name), deliveries with retry, API keys (scopes, reveal once, revoke).
- **Team**: email invitations with role, hashed single-use expiring link (`INVITATION_TTL_HOURS`, default 72), acceptance sets username/password transactionally. Without email delivery the link is shown once to the inviter.
- Developer docs: `/developers/`, `/developers/api/`, `/developers/mcp/`, `/api/v1/openapi.json`.
